# SurveyKit 产品审视与迭代计划（2026-10-28）

审视对象：线上 https://surveykit.cc，`v0.14.0-20261017.driver-analysis`，revision `d0642f9`（与本仓库 HEAD 一致）。
上一份计划 [PRODUCT_ROADMAP_2026-09-30.md](PRODUCT_ROADMAP_2026-09-30.md) 的 S0–S4 已交付，侧重数据口径与报告交付。本次从“线上产品”的角度补充审视，重点看安全边界、首次体验、性能、度量和产品定位。

## 1. 一句话结论

功能深度已经超过多数同类工具：覆盖调研前、数据清洗、分析产出、交付归档全流程，共 25 个工具入口。但它是以**内部单人工具**的形态放在**公网**上的：无登录，所有访问者共享同一个服务端工作区，共享 AI Key 也没有限流。下一阶段要先补齐上线产品该有的边界，再做增长和体验。

## 3. 产品定位需要先做一个决定

后续路线取决于 SurveyKit 接下来服务谁：

| 方向 | 含义 | 对计划的影响 |
|---|---|---|
| **A. 邀请制内测（推荐）** | 面向少量调研团队/研究员，邮箱登录，免费使用，用来验证主路径和留存 | 先做登录隔离、度量、示例项目；不做计费 |
| B. 内部工具 | 只给自己或本团队用 | 用 Cloudflare Access 锁整站即可，跳过增长、SEO、计费相关事项 |
| C. 公开 SaaS | 任何人注册即用 | 在 A 的基础上增加注册、额度、计费、滥用防护和客服，工作量最大 |

推荐 A：能力已经足够深，当前最缺的是真实用户的使用数据，而不是更多功能。下面的计划按 A 编排；B 和 C 的差异在第 5 节说明。

## 4. 迭代计划（按 2 周一个迭代）

### 迭代 0：止血（立即，1–2 天）

1. **只给 AI 研究员加登录（A1，2026-10-28 决定）**：其他工具保持免登录，避免影响留存。在 Cloudflare Zero Trust 中只为 `surveykit.cc/api/research` 路径建立 Access 应用，开启邮箱一次性验证码登录；配置 `CLOUDFLARE_ACCESS_TEAM_DOMAIN`、`CLOUDFLARE_ACCESS_AUD`，并把 `RESEARCH_AUTH_MODE` 切到 `access`。后端已支持；前端需新增登录入口：未登录时浏览器跟随 Access 的跨域跳转会被当作网络错误，需要改为显示“登录后使用”卡片，点击后整页跳转到受保护路径完成登录再返回。
2. **迁移现有数据**：现有数据挂在 `anonymous:shared-workspace` 下，切换后会“消失”。先导出 D1 备份，再把这些项目改归属到你的身份（`sub` 或邮箱）。
3. **AI 代理限流（A2）**：用 Cloudflare WAF Rate Limiting 规则限制 `/api/ai`（例如单 IP 每分钟 20 次），在 OpenCode Go 控制台设置额度告警；若整站上了 Access，A2 风险随之大幅下降。
4. **评估暴露影响**：在 Cloudflare 日志中查看过去 30 天对 `/api/research/*` 的访问来源，确认是否有陌生 IP 读取过客户文件，以决定是否需要告知客户。

验收：无 Cookie 访问 `/api/research/projects` 返回 401；登录后能看到迁移过来的原项目；`/api/ai` 超频返回 429。

### 迭代 1：账号与统一项目（2 周）

- 引入轻量账号体系：沿用 Cloudflare Access 的身份，前端显示当前用户和退出入口。登录只在需要云端保存时出现，本地工具始终免登录。
- **两套项目可选同步（A3）**：不强制合并。工作台的本地项目在登录后可以“同步到云端”，未登录照常使用本地项目；原始数据可以继续只留在本地，界面上标明“本地 / 云端”。
- 若改为开放注册，需评估 Access 免费版用户数上限和国内邮箱验证码送达率，必要时换成自建登录（邮箱魔法链接或微信登录）。
- 项目级数据导出与彻底删除（含 R2 文件和 D1 记录），配合隐私说明页（A8）。
- 验收：同一账号换浏览器能看到全部项目；删除后服务端无残留；隐私页说明每一类数据的去向。

### 迭代 2：首次体验与信息架构（2 周）

- **落地页（A5）**：未登录或首次访问时展示一屏价值说明和 3 个典型场景（概念测试、NPS、价格研究），统一品牌名，补齐 title 和 description。
- **示例项目一键体验**：预置一个包含问卷、数据、交叉表和报告的完整 NPS 示例，新用户 1 次点击即可看到最终交付物。代码里已有各工具的“载入示例”，可以串起来。
- **导航收拢（A6）**：一级只保留“项目 / AI 研究员 / 工具库 / 设置”；25 个工具按 4 个阶段放进工具库，并支持搜索；明确 AI 研究员是主入口，与“AI 方案设计”“AI 问卷设计”的关系写在页面上（或合并）；未知路由显示 404 并引导回首页。
- 验收：5 名未用过的研究员在无指导下，10 分钟内完成“导入示例 → 看到报告”的比例 ≥ 80%。

### 迭代 3：性能与度量（2 周）

- **性能（A4）**：把 21 个独立脚本纳入 Vite 构建；模型模块（cluster、driver、kano、psm、proposal-deck）改为进入对应页面时再加载。目标：首屏可交互 < 3 秒，首页 JS 下载量减半。
- **埋点（A7）**：采用自托管或隐私友好的方案（如 Cloudflare Workers Analytics Engine，或 Umami），只记录事件，不记录内容。关键事件：创建项目、导入问卷、导入数据、生成交叉表、生成报告、导出 PPT/Word、AI 调用成功或失败。
- 建立看板：周活跃研究员、项目完成率（导入数据 → 导出报告）、各工具使用率、AI 失败率。
- 验收：看板上线并连续 2 周有数据；用工具使用率识别出使用最少的 5 个工具，作为下线或合并候选。

### 迭代 4：主路径打磨（2–3 周，内容由迭代 3 的数据决定）

- 按漏斗数据找出流失最大的一步优先打磨。从功能结构看，候选是“导入数据 → 字段识别 → 交叉表”，以及“交叉表 → PPT 报告”。
- 报告质量反馈闭环：在 PPT/Word 导出前后记录研究员对每页的修改（保留/改写/删除），作为 AI 报告质量的真实指标，对接上一份计划第 7 节的“报告返工”指标。
- 小屏修复（A9），保证 ≥ 768px 宽度可用。

### 迭代 5：内测扩展与商业化验证（2 周起）

- 邀请 3–5 个外部调研团队试用，每周回访；增加团队空间（项目共享给同事）。
- 根据 AI 成本和使用数据决定额度策略：每人每月免费额度，超出后需自带 Key（设置页已支持自带 Key）或付费。
- 只有内测留存达标（例如 4 周后仍有 40% 的团队每周使用）再启动计费开发。

### 贯穿各迭代：工程治理（A10）

- 把 `release-driver-20261017` 推到 `survey-worker` 远端作为唯一正式仓库，更新 README 里的“正式工作目录”；外层 `D:/调研工具` 的未提交修改逐项确认后迁入或归档。
- `codex-temp/` 下的阶段副本打包归档后移出工作目录，避免误从旧目录发布。
- 发布改为从 `main` 经 CI 部署，`/healthz` revision 与 `main` 不一致时告警。

## 5. 若选择其他方向

- **B 内部工具**：只做迭代 0（Access 锁整站）和工程治理，然后回到上一份计划的效率路线；迭代 2 的落地页、SEO 以及迭代 5 均可取消。
- **C 公开 SaaS**：迭代 1 需要改为自建注册登录（Access 不适合开放注册），增加邮箱验证、滥用防护、用户级 AI 额度和计费，预计多 3–4 周；隐私条款需要正式法律文本。

## 6. 暂不建议做的事

- 继续增加新的分析模型或工具入口。当前 25 个入口已经超过新用户的理解成本，先用数据确认哪些工具真正被使用。
- 整体重写 `app.js`。沿用上一份计划的原则，随性能拆分逐步迁移。
- 在线答题/发放平台。这与问卷星、腾讯问卷正面竞争，不是当前优势所在。

## 7. 本次审视的范围与限制

- 实测项：首页、工作台、AI 问卷设计页、移动端布局、`/healthz`、`/api/ai`（GET 状态）、`/api/research/projects`（GET 列表）、页面资源加载时序。
- 未实测：AI 生成质量、PPT/Word 导出、数据清洗与交叉表的端到端结果（上一份计划已有验收记录）。
- 为避免接触客户数据，没有打开共享工作区中任何项目的文件、对话或成果，也没有发起写入请求。“可修改、删除”是依据同一身份模型和接口代码得出的判断，未实际验证。
- 性能数据来自单次桌面访问，迭代 3 前应在国内网络环境多次采样，以确定基线。
