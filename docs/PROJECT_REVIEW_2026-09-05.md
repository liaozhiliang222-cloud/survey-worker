## 已确认问题

优先级：P1 为优先阻断错误分析结果，P2 为明确功能/生命周期缺陷。本轮未发现并确认 P0，不代表完成了全面安全审计。

### B1 · P1 · 缺失值被当作 0，NPS 和均值失真

- 位置：[data-engine.mjs](../lib/data-engine.mjs) 第 17、311–345 行；[data-weighting.mjs](../lib/data-weighting.mjs) 第 16、74–77 行。
- 原因：`Number('')`、`Number(null)` 得到 0。总体计算部分先过滤空值，分组与加权分支没有采用相同过滤规则。
- 复现：同组两行 NPS 为 `10`、空白。总体显示 100，但该唯一分组显示 0；两行权重均为 1 时，加权总体也显示 0。数值 `10`、空白的加权均值显示 5。
- 影响：总体与分组矛盾；NPS、均值、有效样本量和基于结果的洞察可能出错。共享数据引擎被本地和云端使用，但本轮复现在本地执行。
- 修复：统一缺失值判定，在数值转换前处理 null、undefined、空串与空白；保留真实 0；让总体、分组和加权采用同一有效样本口径。
- 验收：上述 NPS 均为 100、有效 base 为 1；均值为 10；真实评分 0 仍进入计算；全部缺失时返回无有效数据。

### B2 · P1 · 截尾后的权重分布失配，仍报告收敛成功

- 位置：[data-weighting.mjs](../lib/data-weighting.mjs) 第 47、69–70 行。
- 原因：`converged` 和 `maxDelta` 在截尾前计算；截尾并再次归一化后直接复用旧诊断。
- 复现：A/B 原始样本为 9:1，目标 50%:50%，截尾最大权重 2。输出分布变成 71.43%:28.57%，却返回 `converged=true`、`max_margin_delta=0`；归一化后的最大权重为 2.8571。
- 影响：用户可能接受一个并未达到目标分布的加权版本。
- 修复：以最终输出权重重算所有诊断；明确定义截尾上下界是在归一化前还是最终权重上生效，若承诺最终范围则需同时满足边界。未收敛应明确展示残差与失败原因。
- 验收：该样例实际最大边际差约 0.214286，不能报告零残差收敛；如要求最终最大权重 ≤2，则最终输出必须满足或明确报告约束不可兼得。

### B3 · P1 · 加权数据清洗后，后续分析静默丢弃权重

- 位置：[data-engine.mjs](../lib/data-engine.mjs) 第 448、474 行。
- 原因：清洗总是创建 `type='cleaned'` 的数据集，而交叉表仅在 `type==='weighted'` 时使用 `__weight`。
- 复现：两行 NPS 为 10、0，权重为 2、1；清洗前 NPS=33.3。只执行空行清洗，删除 0 行，清洗后 NPS=0。
- 影响：无损清洗改变研究结论；用户无法从样本量变化发现问题。
- 修复：短期可明确禁止在 Weighted Dataset 上直接清洗，并引导回到 Raw/Clean 后重新加权；如支持该流程，必须保留权重语义并重新评估目标分布、标签与诊断。不能只保留 `__weight` 列。
- 验收：零样本变化不会静默改变 33.3 的结果；有样本变化时必须重新计算/标记加权状态；不允许再次加权而未提示已有权重。

### B6 · P1 · 加权频数表分母包含缺失答案，与非加权口径不一致

- 位置：[data-engine.mjs](../lib/data-engine.mjs) 第 347–350 行。
- 原因：类别列表排除了空值，分组分母却累加全部行的权重，且未把缺失值显示成一个类别。
- 复现：同组两行答案为 `yes`、空白，权重均为 1。非加权表显示 yes=100%，加权表显示 50%，显示的全部类别合计也只有 50%。
- 影响：即使所有权重相等，结果也会改变，用户无法解释百分比差异。
- 修复：统一有效作答 base；如产品允许总样本分母，应显式展示分母选项、缺失类别/缺失量，并在 Excel 与 Evidence 中保留口径。
- 验收：相同有效样本、等权重时，加权与非加权百分比一致；单选类别在有效 base 下合计为 100%（允许舍入误差）。

### B4 · P2 · 同一工作簿的第二张 Sheet 被静默映射到第一张

- 位置：[data-engine.mjs](../lib/data-engine.mjs) 第 63–68 行；本地 store 的 Raw Dataset 去重逻辑也按文件 ID 判断。
- 原因：登记数据集仅以 `source_file_id` 去重，检查在解析请求的 `sheetName` 之前。
- 复现：先登记 SheetA，再明确要求登记 SheetB。两次得到同一 Dataset ID，第二次 metadata 仍为 SheetA。
- 影响：使用多 Sheet API 时可能分析错误工作表。这是已确认的 API 行为，本轮未证明前端已有选择第二张 Sheet 的完整入口。
- 修复：按项目、文件及规范化 Sheet 标识去重，并同步本地/云端存储约束；若只支持单 Sheet，应明确拒绝第二次不一致请求。
- 验收：同 Sheet 重复注册幂等；不同 Sheet 得到对应的数据集，或返回明确的业务限制错误。

### B5 · P2 · 本地删除项目返回成功，但派生数据文件仍保留

- 位置：[research-handler.js](../lib/research-handler.js) 第 511 行；[research-store.js](../lib/research-store.js) 第 162 行。
- 原因：本地 Dataset 保存 `storage_path`，删除逻辑只收集 `dataset.storage_key`，漏掉 Clean/Weighted JSON 文件。
- 复现：对隔离测试项目发出 DELETE，返回 204，项目记录消失；其派生文件仍能通过本地 storage 读取，样例残留 142 字节。
- 影响：用户以为数据已删除，但本地研究数据残留且失去元数据索引。
- 修复：统一存储键适配方法，删除任务纳入全部上传及派生文件；增加失败重试和删除完成核对。
- 验收：项目与全部派生字节均清除；重复删除/部分文件不存在可安全处理；存储删除失败不能被标记为全部完成。
- 范围：确认于本地 Node 路径；不据此断言云端 R2 删除也有相同问题。

### B7 · P2 · 默认 Vite 开发配置把 AI 请求代理回自身

- 位置：[vite.config.js](../vite.config.js) 第 98、105–108 行；[server.js](../server.js) 第 13 行。
- 证据：使用 Vite `resolveConfig` 读取实际配置，开发端口为 4281，`/api/ai` 目标为 `http://127.0.0.1:4281`。
- 触发：4281 空闲时只按 README 执行 `npm run dev`。请求会被代理回同一服务，无法到达真正 AI handler。若先启动占用 4281 的 legacy 服务，Vite 自动换端口，行为又会不同。
- 修复：将共享 AI handler 接入 Vite middleware，或使用明确独立的后端端口并提供统一启动脚本；更新 README。
- 验收：干净环境一个启动命令即可使用 AI API；缺密钥时快速返回规范错误；启动行为不依赖是否已有服务占用端口。
- 验证边界：这是配置解析确认的问题；本轮没有发送递归 HTTP 请求制造连接循环。
